# 有界生成与运行治理规则 v1

本合同落实 P1/P2 整改周期已批准的生成规则，遵循 Workflow / Agentic / Evidence 责任矩阵和 P3 实现决议合同。这里只定义生成控制，不表示后续 D 管线或 P3 运行时代码改道已实现。冻结 P1/P2 在本周期内只读。

## 1. 四条生成规则

- 只对失败段带具体诊断修复，初次生成之后最多两次（`attempt=0,1,2`）。仍不过就以 `degraded-T1` 或 `degraded-T2` 缺口标记交付，其余段继续。远端完成但无效，不再让整个单元终局失败。
- 只禁止**跨运行搬运未被接受的答案**。允许同一次运行内带诊断修复，也允许按精确输入/模板身份复用已接受的段。重跑只做失败或有变更的段，不把过期接受记录洗成当前证据。
- 允许有用段带缺口和声明上限交付。完整冻结批与不可变证据只用于正式出口，不是开发迭代的前置条件。
- 默认本地宽松解析、代码严格校验。无害的表示差异可归一化；无效引用、结构或身份仍须校验失败。provider schema 仅在小而浅时可选；D 默认不用 provider schema。禁止巨型 provider schema，也不让一次原子回答承载整个单元。

## 2. 机械门、判断与模板边界

生成硬门只查结构与身份：ID、引用、每段输出结构、无未登记新事实。槽位上限和渲染成功属于结构检查。语义质量交评审打分或告警，不做内容全覆盖/闭包门。内容缺失是明确的下游反馈；漂亮的 schema 或测试数量不证明业务价值。

Agentic 选择模式、参数、裁剪和有界业务专有文本。Workflow 实例化模式、填槽，按引用生成 provenance 和声明上限，编号、交叉引用并渲染。模型不书写句柄、嵌套组合或变体标签。版本化模板只含章节骨架、模式适用条件/参数和固定表达，不携带业务答案或业务默认值，不按配额凑数。没有匹配模式时允许有界自定义段，并标记待沉淀；报告自定义段占比。

`reference-packages/phase3-implementation-delivery/p3-realization-decisions-contract.md` 的七类保守默认是已批准的风险处置规则，由 Workflow 对缺口决议机械应用；它不授权在模板/脚本中填入场景答案或业务默认值。敏感决议保留 `confirmation_required = true`、来源与声明上限。

生成规则不把失败的运行时测试改判为成功，也不放宽来源/digest 身份。P4 保持只读；现有 OMR → 隔离 SQR 评审语义质量与 T2 决议，不增加评审轮次。正式声明仍由证据封顶。

## 3. 开发期与正式出口

开发期允许单场景单段、经授权的带模板真实调用、修提示后在上限内重跑，以及缓存回放。**单场景单段带模板真实运行**可作为 CP2 证据。区分回放与真实调用，缓存不能冒充新模型运行。独立保留已接受的段和缺口。

冻结批、不可变正式证据和三场景 3/3 只用于正式出口，不阻碍开发中的单段产生有用证据。模型授权和申报上限规则在开发期同样适用；M0 不跑真实模型。

## 4. 单次调用上限

- 请求：≤约 60K token。
- 输出：≤约 8K token。
- 本地 schema 深度：≤3 层。

可能超限时拆段或简化表示，不加预算、重试、规则，也不改用巨型 provider schema。每轮真实运行只动内容、机制、验收严格度中的一条轴，在 issue 和 PR 写明。Stage-05 每场景约 15–25K 输出 token 是多次小调用的建议总量，不是单次许可，待 M1 实测校准。

## 5. 保留运行时减负

不设常设 Plan Challenge 步骤、Integrator 或重复审批；删除生成自评、整包 sufficiency 和固定一次补材料限制。按 ID/digest 选读相关上游片段，仍遵守申报的调用/token 上限。不为补偿失败新增门、角色、控制器、恢复层或审计轮次。

现有评审保持有界 OMR → 隔离 SQR，不把它变成生成自评或新审批控制器。P3 在每切片实现前把 T2/矛盾/不可行缺口批量做一次小调用，先查已有决议、再查委托规则。T0/T1 不为求稳升级。记录仍在现有 Authority Delta 与人读投影中，不新增 Authority 路径/存储。运行时代码按后续 WP 实现，本次文档不声称其已落地。

## 6. 证据与代码分开

代码/合同 PR 不向仓库内的历史运行快照新增文件。运行证据放 WP0.1 确定的制品库并提供只读访问。仓库只留带 sha256 和精确来源/提交身份的索引与摘要，不在代码 PR 复制整套冻结安装包；不改写历史证据。

每次真实模型调用记录一行 JSONL：`run_id`、`wp`、`scenario`、`section` 或 `slice`、`attempt`（0–2）、`request_tokens`、`output_tokens`、`duration_ms`、`parse_ok`、`validate_ok`、`diagnostics`（摘要）、`outcome`、`template_version`、`patterns[]`、`model`、`prompt_sha256`。`outcome` 只取 `accepted`、`repaired`、`degraded-T1`、`degraded-T2`、`failed`。

索引附精确命令、输出、退出码、适用时的 CI 链接、原始记录位置与 sha256。报告单次输出 token 最大/中位数、请求 token 最大值、首次合格率、修后合格率、交付段数/总段数、总 token、调用次数、自定义段占比；从 M1 起加报缺口决议数和委托规则命中率。指标必须能从原始记录复算，不用逐字采用率、测试数量或自评 PASS 代替。

## 7. 授权与人工止损

只有标明“跑模型：是/可能”的 WP 可做真实调用。每轮开跑前在 WP issue 申报目的、唯一改动轴、次数上限、token 上限和终止条件。上限是封顶，不是消费目标；任何超限调用须事先获 Owner 批准。运行中 P3 决议调用达到上限后，不再调用，按保守默认取值并记录。

禁止 run-until-PASS，禁止因预算还剩继续。同一里程碑连续两轮没有可度量进展，或两次验收不通过，必须停止并向 Owner 报告证据与选项，由 Owner 决定缩小范围或下一步方向，不靠新增门/角色/控制器绕开止损。SQR 持续较高的 T2 决议驳回率须交 Owner 作原则变更决定，批准后才可启用角色联合决议。待定的总 token 阈值、决议调用上限、驳回率阈值在 M1 验收申请中按实测提建议，由审计方核定。
