# v1.10 Product Interaction Semantics Authority Boundary v0.1

Status: Issue #1118 P0 frozen design/contract target

This document defines the minimum authority layer needed for mature generated Web interaction without moving concrete UI design into P1/P2.

It is a bounded correction inside the P3 Web Generation detour controlled by #1117. It does not create a new lifecycle phase, a parallel frontend methodology, or a generic P1/P2 redesign program.

## Control rule

```text
P1 owns consumer/product truth.
P2 owns architecture/data/state/security truth plus Product Interaction Semantics.
P3 Action Cards project accepted semantics into implementation obligations.
P3 Agentic owns concrete product interaction and component realization.
Evidence/Gates prove consumption and detect authority drift; they do not choose the UI.
```

The boundary exists because technically valid request fields are not enough to produce a mature consumer interaction. A `string`, `array`, `enum`, or business reference describes contract/data shape; it does not decide what a user should type, discover, select, inherit from context, or never see.

## Ownership matrix

### P1 owns consumer/product context

P1 owns product truth when source evidence or accepted Agentic product judgment can legitimately establish it:

- user role / terminal consumer;
- user job and meaningful task;
- business outcome;
- task frequency or recurring/occasional posture when supported;
- operator proficiency / operating context when supported;
- user-visible business vocabulary;
- material friction and error consequences at product level;
- what the user reasonably expects the system to remember, carry forward, or default when that expectation is product truth.

P1 must not choose widgets, React components, page composition, responsive layout, or concrete interaction patterns merely to make downstream generation deterministic.

### P2 owns architecture truth and Product Interaction Semantics

P2 continues to own accepted operation, contract, data, state, persistence, security, role/visibility, provider, and discovery/read-model authority.

For material consumer-facing fields and decisions, P2 additionally owns a **Product Interaction Semantics** packet. The packet describes what the interaction means and what factual constraints a later product realization must preserve. It does not describe the component that should render it.

The structural contract is:

- `user_meaning`
- `value_source`
- `cardinality`
- `editability`
- `candidate_source`
- `discovery_requirement`
- `context_carryover`
- `default_or_recent_semantics`
- `usage_frequency`
- `error_cost`
- `validation_semantics`
- `privacy_or_sensitivity`
- `free_form_allowed`
- `free_form_rationale`
- `truth_state`
- `unresolved_interaction_gaps`

These fields are semantic questions, not answer templates. Workflow/validation may require the questions to be addressed, but only accepted P1/P2 Agentic authority may decide the values.

`candidate_source` must distinguish an accepted discovery/candidate source from an absent or unresolved one. It must not manufacture an option list because a field name looks enumerable.

`truth_state` must preserve whether the interaction truth is accepted or still bounded/review-bound according to the current authority model. Structural validation does not promote a truth state.

`unresolved_interaction_gaps` is mandatory even when empty. Missing candidate vocabulary, missing List/Search/Lookup authority, unclear defaulting, or unclear free-form legitimacy must remain visible rather than being hidden behind a technically convenient text field.

## Discovery-gap rule

A business reference is not product-ready merely because its contract type is `string`.

When a consumer must provide a reference and no accepted workflow context, current business object, List/Search/Lookup operation, accepted vocabulary, or other candidate source exists, P2 must surface a discovery gap.

P2 may then:

- bind an already accepted candidate/discovery source;
- accept a new architecture capability only when P1/source authority justifies it;
- keep the interaction review-bound and route the missing truth/capability explicitly.

P2 must not invent a catalog or silently tell P3 to accept an opaque internal reference.

## Consumer-outcome and recognizability rule

Discovery is necessary but not sufficient for a mature terminal product. A read model is product-sufficient only when the intended terminal persona can both find the durable object and recognize the correct object using accepted human/business labels or context adequate for the next action. A list of UUIDs, technical status, version counters, or otherwise indistinguishable records does not become product-ready merely because it is queryable.

The same rule applies to successful operation results. When the accepted P1 task promises a user-visible answer, diagnosis, recommendation, explanation, task meaning, or other meaningful outcome, P2 must expose that outcome directly or expose an accepted resolver/read model from which P3 can obtain it. A field named `*_ref`, `*_id`, or equivalent is not consumer-readable content by morphology alone. It may be rendered as business content only when accepted authority explicitly establishes that the referenced value itself is human-readable; otherwise the contract must provide a consumer-readable projection/resolution path or remain review-bound.

For image/file semantics, P2 must preserve a real materialization path: the user-provided file must become an accepted backend/provider-readable resource reference before a downstream operation can claim to consume it. Filename/size pairs, browser-local object descriptions, synthetic `local-*` strings, or other pseudo-references cannot substitute for file bytes or an accepted stored resource.

These are semantic sufficiency rules. They do not select a file picker, card, table, modal, uploader component, or any other concrete P3 presentation.

## Free-form rule

Free-form text is a semantic decision, not the default fallback.

`free_form_allowed=true` requires a reason grounded in product/business meaning. Conversational child questions in BrainyPal are a valid example: natural language is the task itself.

`free_form_allowed=false` does not imply any particular widget. It only tells P3 that the consumer must not be forced to encode structured business meaning as arbitrary prose or storage syntax.

## P3 Action Card projection

P3 Action Cards own the projection of frozen Product Interaction Semantics into implementation obligations.

Valid obligations include:

- preserve multi-value business meaning;
- make accepted candidates discoverable;
- reuse existing consumer-visible business data;
- do not require opaque internal-reference entry;
- do not require the consumer to encode collections using storage syntax such as comma-separated IDs;
- reuse accepted workflow/session context when the value is already known;
- preserve accepted default/recent-value semantics;
- protect high-error-cost actions appropriately;
- permit free text only where the accepted semantics allow it.

Action Cards do not own concrete UI component selection.

## P3 Agentic realization authority

P3 Agentic owns the actual product realization inside frozen P1/P2/Action Card truth, including:

- page and application composition;
- concrete interaction pattern;
- concrete control/component choice;
- layout and information hierarchy;
- progressive disclosure;
- search/filter/sort/bulk realization where justified;
- keyboard/touch interaction details;
- contextual default presentation;
- responsive behavior;
- accessibility realization;
- validation/confirmation presentation;
- business-facing copy and state presentation.

The same Product Interaction Semantics may legitimately produce more than one valid P3 realization.

For post-first-wave product maturity, P3 must also make four implementation-local judgments without turning them into P2 presentation authority or fixed UI rules:

1. **Meaningful Outcome Closure** — identify the user-consumable business result that actually closes the task. Route access, persistence, bounded-role access, reload/re-entry, a completion toast, or an opaque reference are supporting mechanics, not the outcome by themselves.
2. **Decision Context Sufficiency** — human recognizability is necessary but not sufficient. A list, queue, selection, result, or detail surface should expose enough accepted role-appropriate context for the user to choose, prioritize, review, or continue the work confidently.
3. **Operating-scale Interaction Judgment** — reason about plausible working-set size, repeated-use frequency, lookup behavior, recency, prioritization, and whether search/filter/sort/grouping/bulk behavior is justified. This is not a widget quota and does not make any one interaction pattern mandatory.
4. **Longitudinal Work Continuity** — when work spans time or prior records, connect current state with the relevant history/change/provenance and a clear next action so a returning user does not reconstruct the workflow from memory or technical identity.

These are P3 realization questions. Return to P2 only when a correct realization genuinely requires missing business/read/query/history authority; do not reopen P1/P2 merely because P3 must choose a stronger product composition.

Example: a frequent multi-value competitor-reference task backed by an accepted discovery API could be realized as either:

1. a searchable multi-value picker; or
2. a keyboard-oriented typeahead token composer using the same discovery API.

Both can be valid because P2 froze semantic constraints, not a widget.

## Forbidden P2 presentation authority

The following fields are forbidden inside accepted Product Interaction Semantics authority unless an external source explicitly makes the presentation itself authoritative:

- `widget_type`
- `control_type`
- `react_component`
- `html_input_type`
- `use_multiselect`
- `interaction_pattern`
- `component_type`

Equivalent renamed fields that merely smuggle concrete component choice back into P2 are also authority drift.

Forbidden methodology shortcuts include:

```text
string -> input
enum -> select
array -> multiselect
reference -> dropdown
```

Contract/data shape may constrain a realization, but it does not choose one.

## Legacy P2 frontend projection boundary

Older Phase-2 Engineering Spec Pack surfaces contain page `component_type` and enumerated `interaction_pattern` output. Under the v1.10 authority model these are a **legacy review projection**, not accepted Product Interaction Semantics authority.

Compatibility output may remain temporarily visible while #1119 migrates the generation path, but it:

- must not become accepted Product Interaction Semantics authority;
- must not override frozen P1/P2 semantic truth;
- must not force P3 to use a particular control, component library, or interaction pattern;
- must not turn a compatibility renderer into product-design authority.

If an external source explicitly requires a presentation, preserve that requirement as source authority and trace it explicitly. Otherwise P3 remains free to realize the semantics.

## Scenario probes for the first rerun

### GEO

`competitor_refs` and `topic_refs` are multi-value business collections. P2 must preserve cardinality and determine accepted candidate/discovery sources without falling back to comma-separated opaque text.

`prompt_set_ref` is a business reference. If consumers must choose it, its discoverability must be backed by accepted context/data/operation authority or remain an explicit discovery gap.

Period/baseline/task context should not be re-requested when accepted workflow/session semantics already provide it.

### PetClinic

`service_scope_ref`, `work_context_ref`, and `follow_up_context_ref` must not be assumed to be dropdown catalogs or free text from their names alone.

P2 must determine, from accepted authority, whether each is based on existing records, accepted vocabulary, recent values, user-defined business data, genuine free form, or remains unresolved.

### BrainyPal

Natural child questions may remain conversational free form.

Photo input remains image/file semantics when that is the accepted product meaning.

Route correction may remain a constrained choice when accepted route states define the denominator.

Existing records should be discoverable when the user task depends on selecting them, but the semantics must not over-structure natural conversation.

## Evidence/Gate ownership

Evidence/Gates may prove or detect:

- accepted Product Interaction Semantics reached downstream obligations;
- P3 did not mutate frozen P1/P2 truth;
- a structured collection was not flattened into storage syntax;
- a business reference does not require opaque internal-ID knowledge;
- free text is justified by accepted semantics rather than used as a lazy fallback;
- accepted context/default/discovery behavior is real and reload/re-entry safe;
- terminal read models provide human-recognizable **and decision-sufficient** labels/context, not merely technical identity;
- successful operations expose or resolve the user-consumable business outcome and enough next-action context instead of stopping at an opaque reference/status or persistence/re-entry mechanics;
- repeated-use surfaces remain usable at plausible operating scale without imposing search/filter/sort/grouping/bulk controls when the task does not justify them;
- longitudinal work gives returning users enough current-state/history/provenance/next-action continuity where the accepted workflow spans time;
- image/file inputs are materially available to the backend/provider rather than represented by browser-local pseudo-references.

Evidence/Gates must not decide that an array always uses a multiselect, an enum always uses a select, or a page must contain a fixed number/type of controls.

## Structural contract implementation

`scripts/common/product_interaction_semantics.py` is the structural contract helper for this boundary. It owns only:

- required semantic field presence;
- rejection of forbidden presentation-authority keys;
- stable semantic identity/digest binding;
- proof that P3 realization remains non-authoritative for P2 truth.

It deliberately does not enumerate valid widgets, candidate vocabularies, domain values, or preferred interaction patterns.

## P0 freeze and next step

Issue #1118 P0 is complete when:

- this authority boundary is mirrored in release-facing P2 and P3 frontend skill surfaces;
- focused contract tests reject presentation-authority leakage into P2;
- focused contract tests prove more than one P3 control choice can bind to the same frozen semantic packet;
- legacy P2 frontend projection is explicitly downgraded from authority;
- no P3 Web renderer behavior is modified.

After this P0 freeze, #1119 may implement the minimum P1/P2 generation support needed to produce the new semantics. #1119 must not reopen the ownership boundary unless implementation evidence shows a material design contradiction.
