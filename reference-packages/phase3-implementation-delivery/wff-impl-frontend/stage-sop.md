# wff-impl-frontend SOP

1. Confirm frontend is explicitly requested by accepted project/P1/P2/P3 scope. Backend-only work must remain unblocked.
2. Load the exact current UI IA contract, generated shared types/API client, and accepted P3 implementation authority.
3. Verify every requested page and compiled interaction is authoring-ready. If accepted P3 already contains Web targets, preserve that exact denominator. If this is an explicitly requested frozen backend-first continuation with zero Web targets, verify every interaction maps exactly to an existing accepted P3 slice/operation/contract before adding Web-only targets through `p3-authority-delta-frontend-extension`.
4. Run the canonical frontend authoring owner through `run_impl_frontend.py --ui-ia-contract ... --implementation-authority ... --project-artifact-root <project-artifact-root>`; pass the current Authority Delta ledger when the frontend continuation owns new realization records. An aggregate `run_impl.py --enable-frontend` caller may delegate to it only when the selected profile carries the aggregate/runtime dependencies.
5. Treat only exact decision/source/page bindings as Workflow-owned. The generated `apps/web/app/ui-app.tsx` application region plus page/test regions are Host-Agent-owned product realization surfaces; Workflow must not replace the materialized application with a deterministic router/shell.
6. On the first unresolved pass, stop at `authoring-required`; do not reinterpret scaffold generation as frontend completion.
7. Rerun against the same accepted P3 decision after materialization. Reject changes to UI IA content, P3 decision identity, frozen backend target/test denominator, Agentic block denominator, or protected shell instead of silently rebinding prior work. A backend-first frontend extension may add only its explicitly recorded Web target/test denominator; it cannot alter the frozen backend denominator.
8. Preserve typed-client/API-contract/security boundaries. If a missing detail is only implementation-local product realization, the Host Agent decides it in P3 and records the refinement in the P3 implementation decision / Authority Delta. Maintain the corresponding human/project-knowledge projection at the fixed `<project-artifact-root>/p3-realization-decisions.md` path under `../p3-realization-decisions-contract.md`: material product/architecture/UX decisions remain expanded and traceable; incidental implementation-only choices may be indexed without expansion. If the unresolved fact changes business meaning, architecture ownership, interaction/API contract truth, security/permission truth, persistence authority, or another frozen boundary, use a recorded P3 gap decision with `supersedes` for overridden facts. Preserve frozen P1/P2 bytes and queue next-version backport.
9. Materialize a complete consumer-operable frontend realization for the accepted slice: normal product entry, product identity/orientation, usable navigation, domain-appropriate page composition, relevant loading/empty/success/validation/denied/error-retry/not-found behavior, responsive/accessibility treatment, project-locale consumer copy, and human-readable business feedback. Terminal roles must remain independently consumable; do not collapse them into a super-role product path. Internal identifiers must come from response/workflow context or real lookup/discovery surfaces, never raw UUID text entry. A discovered durable record must be human-recognizable **and decision-sufficient** for the target persona using accepted business labels/context; technical identity/status or a thin label alone is not enough when the user must choose, prioritize, review, or continue work. A successful operation must visibly deliver or resolve the **user-consumable business result** rather than stop at route access, persistence, reload/re-entry, a completion toast, or opaque reference; provide enough result/next-action context for the user to understand what happened and what can happen next. For repeated-use/list/queue/selection work, explicitly judge plausible working-set size, frequency, recency and lookup/prioritization needs, and add search/filter/sort/grouping/bulk interaction only when the task justifies it—never to satisfy a widget quota. For longitudinal work, connect accepted current state with relevant history/change/provenance and next action so a returning user need not reconstruct the workflow from memory or technical identity. A request field classified upstream as `source=user-input` must be populated from real user-visible input or an explicitly accepted carried user value; never manufacture a UUID, random token, placeholder, or pseudo-evidence merely to make the request pass. For image/file semantics, first materialize the selected bytes into an accepted backend/provider-readable resource and pass that reference to the business operation; filename/size/browser-local pseudo-refs are disallowed. If accepted read/discovery/outcome/history/materialization authority is missing, resolve it through a P3 gap decision with conservative defaults and a claim ceiling; do not fabricate business data. Keep qualification/gate explanations out of steady-state product copy unless the real user task needs them. When authentication is required, also materialize product-facing sign-in/session/recovery UX inside the frozen security boundary. Use an accepted external IdP when P2 freezes one and keep the local adapter disabled; otherwise P3 may explicitly enable the generated local `/auth/session` adapter with `PHASE3_LOCAL_AUTH_ENABLED=true` as implementation support. These details need not all be pre-authored in P1/P2 when they are legitimately P3 decisions.
10. Keep `impl-frontend-report.json` authoring evidence non-authoritative: no runtime evidence refs, no Trace confirmation, no browser proof, no product/P4 admission.
11. Hand the materialized source to the existing P3 aggregate/runtime-smoke owner. For every current-ready compiled interaction, supply a current `tests/e2e/**` spec carrying the exact frontend runtime marker and exact UI-IA API endpoint. Consumer journeys carry `@wff:frontend-consumer-journey journey_id=... entry_route=... outcome=... [persona_id=...]`; `outcome` must name the user-consumable business result and cannot be satisfied solely by login/route access, persistence, bounded-role access, reload/re-entry, or an internal reference. Multi-role products require one independently bound least-privilege journey per terminal persona. When clean first use is required, also bind `@wff:frontend-clean-first-use journey_id=... [persona_id=...]` to evidence that starts without business seed/fixture identity, performs a real write, performs the required read/discovery, and proves reload/re-entry context recovery. Reject hard-coded/random UUIDs as consumer evidence, and reject any generated request that fabricates a `source=user-input` business value instead of collecting or carrying the accepted human input. For authenticated products, runtime-isolated test credentials may only be typed into the product session UI; reject direct Authorization/identity-header injection, localStorage identity seeding, browser/network interception or synthetic page content. Write/mutation specs must isolate desktop/mobile data via `testInfo.project.name`.
12. Run the accepted API + Web runtime evidence with desktop/mobile Chromium and retained screenshot/Playwright/trace evidence. Preserve the Agentic-authored application, verify unknown routes expose visible recovery, and prove document-level viewport fit with no horizontal overflow; screenshot presence alone is not sufficient viewport evidence. Prove at least one real normal-entry -> product-facing session entry when required -> frontend business action -> accepted server-side auth transport -> API -> persistence/readback/returned-state -> **user-consumable business outcome** chain. The evidence must show what result the user receives and the resulting decision/next-action value; technical persistence/re-entry is supporting continuity proof, not the endpoint. When the task has a successful result path, the evidence must exercise and assert the consumer-visible/consumer-actionable result rather than qualify only an unavailable or failure path; when the task uses a file/image, evidence must prove a real accepted materialized resource reached the backend/provider boundary. Current generated backends must use BFF Bearer transport. An explicitly declared frozen backend-first continuation may use only a Web-side compatibility translation to its already-accepted internal auth-context transport, with backend bytes/decision digest unchanged and a lower claim ceiling. In both modes runtime must observe zero browser-supplied Authorization and zero browser-supplied `x-phase3-auth-context`. Keep this evidence factual and non-authoritative; independent P4 consumer/product review remains later qualification.

P3 runtime gap implementation: Use `scripts/phase3/p3_gap_decisions.py::resolve_slice_gaps` with the existing Journal and shared bounded transport; actual network resends count toward the declared decision-call cap. `load_interaction_gap_context` reads the SHA-bound D freeze and keeps unreviewed author sections as reference only. `p3_fact_registration.py` compares actual OpenAPI, SQL and consumed runtime configuration bytes/hashes with frozen source IDs and registered deltas. Extend the original OMR and isolated SQR subject with `bounded_challenge_binding.p3_gap_review_scope`; retain explicit T2 results and missing coverage using `p3_t2_sqr_metrics`, without another review round. Read-model gaps stay explicit until the registered decision binds an actual OpenAPI operation; existing runtime/browser checks must still prove the consumer read path. A status label or decision record alone is insufficient.

When frozen inputs use a partial/older format without the legacy full P2 chain, the existing `run_impl_frontend.py --frozen-input-decision <file>` entry accepts a P3 host decision with `sources`, `fact_sources` (original ID/value selectors), and `decision`. It verifies original SHA256 and manifest members, records the selected operation scope in the canonical implementation authority, and keeps source gaps and review ceilings. Preserve the source bytes, use the same Authority Delta and existing OMR → isolated SQR, and bind actual realized facts/runtime evidence. This admission cannot create P2/S1B review receipts or promote selected execution into full delivery; existing legacy validation remains unchanged.

Realized-fact inventory follows the actual representation: resolve local OpenAPI references and JSON `contentSchema` fields; use the explicit `sqlite-ddl` format for supported SQLite tables, simple indexes and immutable-row triggers. Register each complete SQLite definition so constraints cannot disappear behind column parsing. Unsupported DDL remains an evidence gap. A consumed config may supply `x-wff-fact-id` to distinguish a representation from an original source ID, while preserving its runtime ID and meaning. Zero unregistered facts proves registration only; semantic review findings and runtime limitations remain authoritative.
