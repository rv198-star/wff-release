# wff-impl-action-cards SOP

1. Read the Phase-2 implementation entry and Engineering Spec Pack.
2. Resolve source authority from canonical P2 JSON bridges before markdown fallback.
3. When accepted Product Interaction Semantics exist, retain their exact semantic identity/digest, resolve linked P1 task-frequency/low-step context, and classify component responsibility before rendering: consumer-facing Service cards own consumer interaction obligations; Repository cards retain semantic trace as persistence context and own only persistence-relevant cardinality/validation/sensitivity constraints. This is never a widget instruction. If an older retained P2 bridge matrix does not yet contain this projection, recompute it from accepted P2 authority in P3 memory and leave frozen P2 evidence untouched.
4. Convert material component-owned interaction constraints into explicit verification obligations, then create ActionCards by component, operation, risk, interaction obligation, and verification obligation without selecting concrete controls/components unless presentation is explicitly source-authoritative. Keep complete trace/digest identity but collapse repeated source/obligation text so the human card remains implementation-readable.
5. Mark missing source authority as `review-bound` instead of filling by name inference.
6. Run the official ActionCard runtime.
7. Review the generated report before allowing downstream implementation.

Exit only when ActionCards expose what implementation and tests must prove.
